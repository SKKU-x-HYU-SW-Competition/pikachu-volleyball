# decide 함수와 스냅샷

봇이 게임과 주고받는 계약(약속)을 전부 정리한 페이지입니다. **이 페이지만 잘
읽으면 봇을 짤 수 있습니다.**

## 봇 실행 모델 — 큰 그림 먼저

여러분이 짠 파일은 게임 시작 순간 **딱 한 번 통째로 실행**됩니다. 이 실행에서
`decide`라는 이름의 함수를 정의해두면, 게임 엔진이 그 함수를 **매 틱마다**
새 스냅샷과 함께 호출합니다.

```
파일 로드 (한 번만)
    │
    ├─ var/전역 초기화, 헬퍼 함수 정의
    └─ decide 함수 정의
        │
        └─ [tick 1] decide(snapshot₁) → {x, y, hit}
           [tick 2] decide(snapshot₂) → {x, y, hit}
           [tick 3] decide(snapshot₃) → {x, y, hit}
           ...
```

여기서 나오는 두 가지 중요한 결론:

1. **`decide` 밖에 선언한 변수는 틱 사이에 값이 유지됩니다.** "직전 틱에 공이
   어디 있었는지" 같은 걸 기억하고 싶으면 파일 최상위에 변수를 두고 `decide`
   안에서 갱신하면 됩니다.
2. **`decide` 하나에서 너무 오래 있으면 무입력 처리됩니다.** 상세는 아래 "시간
   예산" 절.

## 함수 시그니처

### JavaScript

```js
function decide(snapshot) {
  // ...
  return { x: -1|0|1, y: -1|0|1, hit: 0|1 };
}
```

### Python

```python
def decide(snapshot):
    # ...
    return {'x': -1, 'y': 0, 'hit': 0}
```

Python의 경우 `snapshot`은 `dict`라 `snapshot['ball']['x']`처럼 접근합니다.
필드 이름은 두 언어 완전 동일합니다.

## 반환값: `{x, y, hit}` 3가지

이 세 필드가 봇이 매 틱 내릴 결정의 전부입니다.

| 필드 | 허용값 | 의미 |
|---|---|---|
| `x` | `-1`, `0`, `1` | 왼쪽 / 가만히 / 오른쪽 이동 |
| `y` | `-1`, `0`, `1` | 위(점프·상방스매시) / 가만히 / 아래(하방스매시) |
| `hit` | `0`, `1` | 파워히트 발동 여부. 지상에서 `x≠0`이면 다이빙 |

**주의**: 이 세 값은 게임 원작의 "좌·우·점프·파워히트" 4버튼과 정확히 대응하는
게 아닙니다. 몇 가지 파생 규칙이 있습니다:

- **점프**는 별도 필드가 없습니다. **땅에 있는 상태(`self.state === 0`)에서
  `y = -1`을 보내면** 그 순간 점프합니다.
- **파워히트의 스매시 각도**는 `hit = 1`을 보내는 그 순간의 `y` 값으로 결정됩니다:
  - `y = -1` → 위로 아치를 그리며 넘기는 스매시 ("못박기"로 흔히 부름)
  - `y =  0` → 직선 스매시
  - `y =  1` → 아래로 꽂히는 강스매시
- **다이빙**은 **땅에 있으면서 `x ≠ 0`이고 `hit = 1`**일 때 발동합니다.

### 같은 값을 여러 틱 계속 보내도 안전합니다

`hit = 1`을 여러 틱 유지해도 파워히트가 중복 발동되지 않습니다. 엔진이 상태
전이로 알아서 막습니다 (파워히트 시작 순간 `self.state`가 `1`→`2`로 바뀌어서
다음 틱엔 `hit = 1`을 보내도 조건 자체가 안 맞음).

### 잘못된 값을 돌려주면?

- 값 범위 밖 (`x = 5` 같은 것)
- 필드 누락
- `undefined`/`None` 반환
- `decide` 안에서 예외 발생

**전부 그 틱 하나만 "무입력(`x=0, y=0, hit=0`)"으로 처리하고 계속 진행합니다.**
이전 틱의 값을 유지하지도, 봇을 종료하지도 않습니다.

## 스냅샷: 봇이 매 틱 받는 정보

한눈에 보이는 예시:

```json
{
  "tick": 12345,
  "side": "LEFT",
  "self": { "x": 120, "y": 244, "state": 0, "frameNumber": 3, "divingDirection": 0 },
  "opp":  { "x": 300, "y": 180, "state": 1, "frameNumber": 5, "divingDirection": 0 },
  "ball": { "x": 216, "y": 140, "xVelocity": -3, "yVelocity": 6,
            "expectedLandingPointX": 340, "isPowerHit": false },
  "meta": { "score": { "self": 7, "opp": 6 }, "isPlayer2Serve": false, "rallyFrameCount": 42 },
  "config": { "tickFrameGroupSize": 3 }
}
```

아래에서 필드별로 자세히 봅니다.

### 좌표계부터 짚고 가기

- 원점은 **화면 좌상단**입니다.
- `x`는 오른쪽으로 갈수록 증가.
- **`y`는 아래쪽으로 갈수록 증가합니다.** "바닥이 0"이 아닙니다. 코트 바닥에
  캐릭터가 서 있을 때 `y = 244`, 공중 최고점은 `y`가 오히려 작아집니다.
- 단위는 원작 게임의 픽셀 그대로입니다. 별도 정규화 없이 정수로 옵니다.

**중요 상수** (직접 파일에 상수로 박아 쓰면 됩니다):

| 이름 | 값 | 뜻 |
|---|---|---|
| `GROUND_WIDTH` | `432` | 코트 전체 폭 (x 범위: 0 ~ 432) |
| `GROUND_HALF_WIDTH` | `216` | 네트 x좌표 (즉 왼쪽/오른쪽 코트의 경계) |
| `PLAYER_TOUCHING_GROUND_Y_COORD` | `244` | 플레이어가 땅에 서 있을 때의 y |
| `BALL_TOUCHING_GROUND_Y_COORD` | `252` | 공이 땅에 닿았을 때의 y |
| `BALL_RADIUS` | `20` | |
| `PLAYER_HALF_LENGTH` | `32` | 플레이어 히트박스의 반폭·반높이 |
| `NET_PILLAR_HALF_WIDTH` | `25` | 네트 기둥의 반폭 (기둥은 x = 216 ± 25) |
| `NET_PILLAR_TOP_TOP_Y_COORD` | `176` | 네트 기둥 상단 상단부 y |

### `tick` — 단조 증가 정수

이번 매치 시작 이후 몇 번째 tick인지. 시간을 재고 싶다면 밀리초로:
`tick * 40 * config.tickFrameGroupSize` (아래 [config 절](#config--게임-실행-설정) 참고).

### `side` — `"LEFT"` 또는 `"RIGHT"`

**내가 어느 쪽 코트를 담당하는지.** `self`는 이 side의 캐릭터, `opp`는 반대편.

**같은 파일이 LEFT/RIGHT 어느 쪽에도 배치될 수 있으므로**, "네트 방향"이나
"내 코트 범위" 같은 걸 하드코딩하지 말고 매번 `side`를 보고 판단하는 습관을
들이는 게 좋습니다:

```js
var towardNet = s.side === 'RIGHT' ? -1 : 1;   // 네트 쪽으로 가는 x 방향
var ownCourtMinX = s.side === 'RIGHT' ? 216 : 0;
var ownCourtMaxX = s.side === 'RIGHT' ? 432 : 216;
```

### `self` / `opp` — 두 플레이어

**둘 다 완전 대칭 정보**를 줍니다. 상대의 위치·상태를 숨기지 않습니다 —
실제로도 사람이 화면을 보면 다 보이는 정보이기 때문에.

| 필드 | 값 | 뜻 |
|---|---|---|
| `x`, `y` | 정수 | 캐릭터 중심 좌표 |
| `state` | 0 ~ 6 | 현재 캐릭터 상태 (아래 표) |
| `frameNumber` | 정수 | 현재 상태의 애니메이션 프레임 번호 |
| `divingDirection` | -1, 0, 1 | 다이빙 중이라면 어느 방향으로 |

**`state`가 특히 중요합니다** — 이 값이 뭐냐에 따라 봇이 무슨 조작을 낼 수
있는지가 달라집니다:

| `state` | 뜻 | 조작 가능성 |
|---|---|---|
| `0` | **정상** (서 있거나 걷는 중) | 자유롭게 이동·점프·다이빙 |
| `1` | **점프 중** | 이동은 그대로. 파워히트 가능 |
| `2` | **파워히트 발동 중** | 이번 파워히트가 끝날 때까지 다른 조작 무시 |
| `3` | **다이빙 중** | 다이빙 궤적을 따라감. 조작 무시 |
| `4` | **누워있음** (다이빙 착지 후) | 몇 프레임 못 움직임 |
| `5` | **승리 포즈** (라운드 종료) | — |
| `6` | **패배 포즈** (라운드 종료) | — |

봇의 조작이 실제로 반영되는 건 대부분 `state === 0` 또는 `state === 1`일
때입니다. 나머지 state에서는 `x/y/hit`를 뭘 보내든 그 순간 캐릭터가 이미
"바쁜" 상태라 무시됩니다 (엔진이 알아서 처리하니 봇에서 특별히 방어할 필요는
없고, "왜 내 이동이 씹혔지?" 싶을 때 이 표를 떠올리면 됩니다).

`frameNumber`는 애니메이션 재생 프레임입니다. 대부분 무시해도 되지만, 파워히트
발동 이후 몇 프레임이 지났는지 등을 정밀하게 세고 싶다면 참고할 수 있습니다.

### `ball` — 공의 상태

| 필드 | 값 | 뜻 |
|---|---|---|
| `x`, `y` | 정수 | 공 중심 좌표 |
| `xVelocity`, `yVelocity` | 정수 | 프레임당 이동량. `yVelocity > 0`은 **아래로** 떨어지는 중이라는 뜻 |
| `expectedLandingPointX` | 정수 | **엔진이 계산해준 예상 낙하지점의 x좌표** |
| `isPowerHit` | boolean | 마지막으로 친 것이 파워히트였는지 |

**`expectedLandingPointX`가 이 스냅샷의 스타 필드입니다.** 엔진이 매 프레임
공의 궤적을 시뮬레이션해서, 공이 땅에 닿을 예정인 지점을 미리 계산해둡니다.
네트 충돌·중력까지 다 반영된 값이므로, 봇의 "어디로 가야 하나" 판단은 대부분
이 값 하나로 처리됩니다:

```js
// 예상 낙하지점을 향해 걸어간다
var dx = s.ball.expectedLandingPointX - s.self.x;
if (Math.abs(dx) > 8) x = dx > 0 ? 1 : -1;
```

이 값을 안 주면 모든 참가자가 각자 탄도 시뮬레이션을 다시 구현해야 하는데,
그건 대회의 흥미 포인트가 아니라고 판단해 노출했습니다.

**주의**: 이 값은 "지금 이 순간의 예상"입니다. 공을 누가 다시 치거나 네트에
부딪히면 다음 틱에 값이 확 바뀝니다. 지난 틱의 값을 그대로 믿지 말고 매 틱
새로 읽으세요.

내 캐릭터·상대의 속도가 필요하면? — 자신은 직전에 자기가 낸 `x` 입력이 곧
속도(수평 이동은 관성이 없음)이고, 상대 속도는 직전 스냅샷의 `opp.x`와
비교하면 됩니다. 엔진이 따로 제공하지 않습니다.

### `meta` — 매치 상태

| 필드 | 뜻 |
|---|---|
| `score.self`, `score.opp` | 현재 스코어 (내 관점) |
| `isPlayer2Serve` | 다음 서브를 오른쪽(Player 2)이 넣는지. 서브 후엔 즉시 갱신됨 |
| `rallyFrameCount` | 이번 랠리가 시작된 이후 몇 프레임이 지났는지 |

**대회 룰**: **10점 선착제**, 서브권은 매치 시작 시 랜덤으로 정해집니다.
세트 수(단판/3판2선승 등)는 차후 결정 예정입니다.

`rallyFrameCount`는 "서브 직후 몇 프레임"을 판별해서 특수 로직을 넣고 싶을 때
씁니다 (예: 랠리 시작 초반엔 서브 궤적이라 예측이 다른 경우).

### `config` — 게임 실행 설정

| 필드 | 값 | 뜻 |
|---|---|---|
| `tickFrameGroupSize` | 정수 (기본 `3`) | 몇 개의 게임 프레임을 하나의 봇 tick으로 묶는지 |

원작 게임은 25 FPS(1프레임 = 40ms)로 돕니다. **`tickFrameGroupSize = 3`이라는 건
봇의 `decide`가 3프레임(= 120ms)마다 한 번씩 호출된다**는 뜻입니다. 이 값은
대회 준비 중 조정될 수 있으니 하드코딩하지 말고 스냅샷에서 읽으세요.

실제 시간(ms)이 필요하면:
```js
var elapsedMs = s.tick * 40 * s.config.tickFrameGroupSize;
```

## 시간 예산

두 개의 다른 임계값이 있으니 헷갈리지 마세요.

- **목표: tick 주기인 120ms 안에 리턴.** 이 안에 끝내야 결과가 다음 tick에
  정상 반영됩니다. 넘기면 그 결과는 "다음 다음 tick"에나 반영되고, 그 사이의
  tick엔 이전 결과가 그대로 씹혀서 반응이 눈에 띄게 늦어집니다.
- **Hard timeout: 360ms** (`= 프레임 40ms × TICK_FRAME_GROUP_SIZE 3 × 3배`).
  이걸 넘긴 응답은 **폐기되고 그 tick은 무입력** 처리됩니다.
  120ms의 3배로 넉넉히 잡은 이유는, Python + Pyodide 첫 콜의 워밍업이나
  가끔 튀는 GC/스케줄 지연까지 흡수하기 위해서.
- **15 tick 연속** hard timeout이면 봇 워커가 강제 재시작됩니다. 파일이 다시
  로드되므로 전역 상태는 다 날아갑니다.
- 무한루프를 돌리면 상대/게임은 안 멈추고 이쪽 봇만 무입력이 계속 나오다가
  결국 위의 강제 재시작까지 갑니다.

**한마디로**: 평소엔 120ms 목표로 짜고, 360ms는 "그 이상 걸리면 진짜 큰일"의
상한선으로 이해하세요.

## 반응 지연은 구조적으로 존재합니다

브라우저 특성상 게임 엔진이 봇의 응답을 그 자리에서 동기적으로 기다릴 수 없어서,
**항상 약 1틱(≈120ms)의 파이프라인 지연이 있습니다.** 즉 지금 tick의 `decide`가
낸 결과는 실제로 그 다음 tick에 반영됩니다. 사람이 키보드로 조작할 때와 비슷한
수준이고, 두 봇 모두 똑같이 겪는 지연이라 승부에 영향은 없지만, "왜 공이 오는
게 보였는데 반응이 늦었지?" 싶을 땐 이걸 떠올리세요.

## 사용 가능한 API·라이브러리

### JavaScript 봇

- 표준 JS 전역: `Math`, `Date`, `JSON`, `Array`, `Map`/`Set`, `console.log` 등
- **불가능**: `import`, `require`, `fetch`, DOM 접근, `window`/`document`. Web Worker
  안에서 도는 격리된 환경이라 그렇습니다.

### Python 봇

- Python 3 표준 라이브러리 전체 (`math`, `random`, `heapq`, `collections`, ...)
- **`numpy` 사용 가능** — `import numpy as np`
- **불가능**: `scipy`, `pandas`, `scikit-learn` 등 그 외 서드파티. 파일 I/O, 네트워크 접근

Python 봇 특유의 주의사항은 [Python 봇 특이사항](python.md)에 정리했습니다.
