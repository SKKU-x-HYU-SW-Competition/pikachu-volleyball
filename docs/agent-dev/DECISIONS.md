## RESOLVED

### D-001. 틱 길이 (몇 프레임 = 1 틱?)

- **왜 막혔는지**: 원작 기본값은 25fps=40ms/프레임이며 현재 stub은 "1 프레임 = 1 틱"이지만,
  참가자 봇이 40ms 안에 연산을 끝내기엔 타이트할 수 있다는 우려가 있었음.
- **결정 내용**: **`tickFrameGroupSize = 1`(원본 그대로 매 프레임)로 확정.** `gameLoop()`은
  `deltaTime` 보정 없이 "호출 1번 = 프레임 1개 전진"하는 구조라([`main.js:156-158`](../../src/resources/js/main.js#L156-L158))
  계산이 40ms를 넘겨도 게임이 깨지거나 desync되지 않고 체감 fps만 잠깐 떨어짐 — "실시간 데드라인을
  못 지키면 오류"인 시스템이 아님. 규칙 기반 로직(비교/분기 몇 개)은 마이크로초 단위라 40ms에 수백~수천
  배 여유가 있고, 진짜 위험(무한루프로 메인 스레드가 멈추는 것)은 틱을 늘려도 해결되지 않으므로
  D-002/D-003에서 다룸. 나중에 학습 기반 봇의 매틱 추론 비용이 실측으로 문제가 되면 그때 값을 올리는
  쪽으로 재논의.
- **결정자**: Claude Code (사용자 승인)
- **결정일**: 2026-07-07
- **반영**: [CONTRACTS.md](CONTRACTS.md) §2

### D-002. 틱 시간초과(또는 잘못된 반환값) 시 처리

- **왜 막혔는지**: 참가자 봇 함수가 예산(D-001) 안에 응답하지 못하거나 형식이 잘못된 값을 반환하면
  어떻게 할지 안 정해짐 — 이전 입력 유지 / 무입력(0,0,0) 처리 / 해당 라운드 실격 중 선택 필요.
- **결정 내용**: **무입력(`x=0, y=0, hit=0`)으로 확정.** 기존 두 입력 소스(`PikaKeyboard`, 기본 AI인
  `letComputerDecideUserInput`)가 이미 매 틱 0으로 리셋한 뒤 그 틱에 확정된 것만 채우는 방식이라
  ([`physics.js:804-806`](../../src/resources/js/physics.js#L804-L806)), "이전 값 유지"는 이 엔진에
  없던 세 번째 규칙을 새로 만드는 셈이 됨. 한 틱 놓치는 건 어차피 체감이 안 되고, 여러 틱을 연달아
  놓치는 상황(행)에서는 "이전 입력 유지"가 오히려 의도치 않은 반복 발동(예: 타임아웃 시작 시점에
  `hit=1`을 들고 있었다면 착지할 때마다 다이빙이 계속 재발동)으로 이어질 수 있어 무입력이 더 안전.
  실격은 일시적 지연(GC 멈칫 등)까지 처벌하게 되어 과함 — 다만 N틱 연속 타임아웃 같은 "지속적인 행"에
  대한 운영진 알림/에스컬레이션은 이번 결정 범위 밖이며, Phase 3(제출/중계) 설계 시 별도로 다룸.
- **결정자**: Claude Code (사용자 승인)
- **결정일**: 2026-07-07
- **반영**: [CONTRACTS.md](CONTRACTS.md) §1.1

### D-003. 봇 코드 실행 방식 (샌드박싱 필요 여부)

- **왜 막혔는지**: 참가자가 짜온 JS 코드를 브라우저에서 동적으로 로드해야 함. 대회 현장 PC에서
  도는 코드라 최소한의 격리가 필요한지, 대회 성격상(폐쇄망, 운영진 사전 검수) 굳이 필요 없는지 미정.
- **결정 내용**: **Web Worker + 타임아웃 + `terminate()` 후 재시작으로 확정.** 같은 스레드에서
  `eval`/동적 `import`로 직접 돌리면 무한루프 하나가 게임 전체(렌더링·상대 입력 포함)를 멈춰버리고,
  동기 코드는 밖에서 끊을 방법이 원천적으로 없음. Worker로 분리하면 `postMessage`로 스냅샷을 보내고
  D-002의 타임아웃 안에 응답이 없으면 무입력 처리, 반복되면 강제 종료 후 재시작해서 나머지 경기는
  영향받지 않게 할 수 있음. 이번 대회는 참가자 신원이 확인되고 운영진이 사전 검수하는 친선전이라
  위협 모델상 "악성 코드 차단"보다 "현장에서 버그 하나가 시연 PC를 멈추는 것 방지"가 실질적 리스크로
  판단, iframe sandbox 등 더 무거운 보안 격리는 후순위로 미룸.
- **결정자**: Claude Code (사용자 승인)
- **결정일**: 2026-07-07
- **반영**: [CONTRACTS.md](CONTRACTS.md) §1.0/§1.3 (신규), §2

### D-006. `expectedLandingPointX`(공 예상 착지점)를 스냅샷에 노출할지

- **왜 막혔는지**: 엔진이 매 프레임 계산해두는 값([`physics.js:323`](../../src/resources/js/physics.js#L323))을
  그대로 줄지, 숨겨서 봇이 직접 탄도 시뮬레이션을 하게 할지는 난이도/재미 설계 문제라 임의로 정하지 않음.
- **결정 내용**: **노출한다.** 기본 탑재 AI의 포지셔닝/점프 판단이 전부 이 값에서 나오므로
  ([`physics.js:808-857`](../../src/resources/js/physics.js#L808-L857)) 이건 "AI의 비밀"이 아니라
  반응이 성립하기 위한 기반값으로 판단. 숨기면 모든 참가자가 네트 충돌 포함 동일한 시뮬레이션 루프를
  각자 재구현하느라(변별력 없는 보일러플레이트 + 틱 예산 추가 소모 + 엣지케이스 불일치로 인한 디버깅
  낭비) 현장 시간을 깎아먹을 뿐, 전략적 변별력에는 기여하지 않는다고 판단. 변별력은 "낙하 지점이
  주어졌을 때 어떻게 움직이고 언제 점프/스매시할지" 전략에서 나오게 함.

### D-007. 좌표 변환 방식

- **왜 막혔는지**: 원본 엔진은 y가 아래로 증가하는 스크린 좌표계(바닥이 `y=244`/`252`, `y=0`이
  화면 최상단)를 쓰는데, 이걸 "바닥=0, 위로 증가"하는 직관적 좌표로 변환해서 줄지, 원본 그대로
  줄지 미정이었음.
- **결정 내용**: **변환 없이 원본 정수 픽셀 좌표를 그대로 노출한다.** 물리 엔진이 전부 정수 픽셀 +
  `| 0` 절삭 연산으로 되어 있어서, 임의로 스케일/축을 바꾸면 봇이 궤적을 정밀 예측하려 할 때 오차
  요인만 늘어남. 원본 코드와 1:1로 대응시키는 편이 구현 리스크도 낮음.

### D-008. 세트제 도입 여부

- **왜 막혔는지**: 브레인스토밍 초안에 `meta.set`/`max_set` 필드가 있었는데, 실제 엔진(`pikavolley.js`)은
  단판(`winningScore=15`)까지만 지원하고 다세트 구조가 없음. 세트제를 넣으려면 컨트롤러 레벨 로직을
  새로 만들어야 함.
- **결정 내용**: **도입하지 않는다.** 다판 대결이 필요하면 엔진 안에 세트 개념을 넣지 않고, 운영
  스크립트 레벨에서 그냥 여러 판을 실행하는 방식으로 처리. 프로토콜/엔진에 부담을 얹지 않음.
