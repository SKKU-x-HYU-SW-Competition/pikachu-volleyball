# ADR-0025 — 게이지 충전 속도 대비 claw 비용 (봇 대전에서 스킬이 거의 안 나옴)

| | |
|---|---|
| 상태 | **OPEN — 회의 안건** (측정 결과만 정리, 수치는 미결정) |
| 제기일 | 2026-08-12 |
| 제기자 | Claude Code (봇 대전 계측 중 발견) — imtmtl 지시로 봇 2종 작성하다 드러남 |
| 관련 | [ADR-0020](ADR-0020-gauge-system.md)(충전 규칙), [ADR-0021](ADR-0021-claw-skill.md) §3·§5-1(수치는 stub), [ADR-0024](ADR-0024-rally-boundary-for-skills.md)(충전 기회 축소), [ADR-0026](ADR-0026-touch-limit-vs-smash-logic.md) |
| 코드 | `skill/gauge.js`(`GAUGE_ON_RECEIVE`), `skill/claw.js`(`CLAW_COST`) — **이 ADR은 코드를 바꾸지 않는다** |

## 배경

[ADR-0021 §5-1](ADR-0021-claw-skill.md)이 "밸런스 수치는 봇 대전 기준으로 다시 잡아야 한다"고
남겨둔 항목이다. 실제로 봇 대전을 돌려보니 **스킬이 거의 발동되지 않는다**는 게 확인됐다.

`docs/agent-dev/example-bots/claw_landing_point_bot.js` / `claw_opponent_position_bot.js`를 양쪽에
붙이고 Playwright로 계측한 결과(90초, 랠리 9~10회, `GAUGE_ON_RECEIVE = 10` / `CLAW_COST = 50`):

| | 90초 동안 관측된 게이지 최댓값 | 발동 횟수 |
|---|---|---|
| LEFT | **20** | 0 |
| RIGHT | **40** | 0 |

두 봇 모두 "게이지가 있으면 쏜다"가 아니라 "쏠 수 있으면 쏜다"로 짜여 있는데도, **비용 50에 한
번도 도달하지 못했다.** 다른 90초 판에서는 양쪽 1회씩 발동했다. 즉 한 경기에 스킬이 0~1번
나온다.

조준 방식 비교(이 봇 2종의 본래 목적)를 하려면 발동 표본이 필요해서, 계측 스크립트에서 **매 프레임
양쪽 게이지를 100으로 강제 충전한 인위적 조건**을 따로 만들어야 했다. 그 조건에서는 판당 20~30회
발동한다. 비교는 됐지만, 그건 현재 수치의 게임이 아니다.

## 원인 (수치 하나만의 문제가 아니다)

`CLAW_COST / GAUGE_ON_RECEIVE = 50 / 10` → **리시브 5회를 한 경기 안에 누적**해야 한 번 쓴다.
게이지는 랠리를 넘어 누적되고 경기 시작 시에만 리셋되므로([ADR-0020](ADR-0020-gauge-system.md))
원래는 도달 가능한 값이지만, 이후 들어온 두 가지가 충전 기회를 같이 깎았다:

1. **[ADR-0024](ADR-0024-rally-boundary-for-skills.md) 랠리 경계 정정** — 착지 후 슬로모션 약
   1.2초 동안 공을 쳐서 게이지를 벌던 경로가 (의도대로) 막혔다. ADR-0024 §봇 밸런스가 이미
   "수정 전 수치 감각은 참고치가 아니다"라고 경고해둔 그대로다.
2. **자기 진영 5회 터치 제한**(`rules/touchLimit.js`, `develop`에서 유입) — 랠리가 짧아진다.
   같은 계측에서 랠리 11회 중 7회가 착지가 아니라 터치 제한으로 끝났다. 랠리가 짧으면 접촉도
   적고, 접촉이 적으면 게이지도 안 찬다. 자세한 건 [ADR-0026](ADR-0026-touch-limit-vs-smash-logic.md).

즉 **`GAUGE_ON_RECEIVE`와 `CLAW_COST` 둘 다 그 두 변경 이전의 감각으로 정해진 stub**이고, 지금은
그 전제가 사라졌다.

## 선택지 (회의에서 정할 것)

어느 쪽이든 코드 한 줄이므로, 논점은 "얼마"가 아니라 **"스킬이 한 경기에 몇 번 나오는 게임을
원하는가"** 다.

| 안 | 방법 | 성격 |
|---|---|---|
| A | `CLAW_COST`를 낮춘다 (예: 50 → 30) | 스킬 빈도만 올린다. 게이지 바가 차는 속도(연출)는 그대로 |
| B | `GAUGE_ON_RECEIVE`를 올린다 (예: 10 → 15~30) | 게이지 바가 눈에 띄게 움직인다. 랠리를 길게 끄는 쪽이 유리해짐 |
| C | 충전 이벤트를 늘린다 (서브·스매시 성공 등에 가산) | [ADR-0020](ADR-0020-gauge-system.md)의 충전 규칙 자체를 다시 여는 것 |
| D | 그대로 둔다 — "한 경기에 한 번 쓰는 필살기" | 현재 상태가 의도라면 유효한 선택. 다만 참가자에게 그렇게 명시해야 함 |

**A와 B는 체감이 다르다.** A는 같은 속도로 차되 빨리 쓰는 것이고, B는 게이지 바 자체가 빨리
움직인다. 관전 화면에 게이지 바가 그려져 있으므로([ADR-0020](ADR-0020-gauge-system.md)) 중계
관점에서는 B가 더 보인다.

## 정할 때 주의할 것

- **`config.gauge`/`config.claw`는 매 틱 스냅샷으로 나간다**([CONTRACTS.md](../CONTRACTS.md) §1.2.1).
  값을 바꿔도 봇이 하드코딩하지 않는 한 자동으로 따라오므로 **CONTRACTS 버전은 올리지 않는다**
  (VERIFY §4 기준 계약 변경이 아님). 단 §1.2 예시 JSON과 `04-bot-writing-guide.md`의 숫자는 같이
  고쳐야 한다 — 이번에 `CLAW_WIDTH` 96 → 60을 바꿨을 때 세 문서가 96에 멈춰 있었다.
- **[ADR-0026](ADR-0026-touch-limit-vs-smash-logic.md)을 먼저 정하는 게 순서상 맞다.** 터치 제한
  수치가 바뀌면 랠리 길이가 바뀌고, 랠리 길이가 바뀌면 여기서 정한 충전 속도가 다시 틀어진다.
- 측정할 때는 **봇 대 봇으로** 볼 것. 사람이 치면 랠리 길이가 달라 감각이 맞지 않는다. 계측
  방법은 이 ADR을 만든 스크립트와 동일하게 `window.__pikaSkills.gaugeTracker.gauges`를 프레임마다
  읽으면 된다.

## 현재 작업 상태 (참고)

2026-08-12 기준 `GAUGE_ON_RECEIVE`는 작업 트리에서 손으로 바꿔가며 시험 중이고(10 → 30 → 15)
**커밋되지 않았다.** 저장소에 커밋된 값은 여전히 `10`이다. 회의에서 확정한 뒤 커밋하면서
CONTRACTS §1.2 예시(`"onReceive": 10`)도 같이 맞출 것.
