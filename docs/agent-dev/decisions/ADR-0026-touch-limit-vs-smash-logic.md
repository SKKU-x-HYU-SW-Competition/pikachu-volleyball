# ADR-0026 — 5회 터치 제한과 원작 AI의 "확실할 때만 스매시" 로직이 충돌한다

| | |
|---|---|
| 상태 | **PARTIAL** — 참가자 가이드 문서화는 완료(§6.6), **규칙 수치는 회의 안건** |
| 제기일 | 2026-08-12 |
| 제기자 | Claude Code (봇 대전 계측 중 발견) — imtmtl의 "공을 잘 못 받는다" 제보에서 출발 |
| 관련 | `rules/touchLimit.js`(SeungJoon, `develop`에서 유입), [ADR-0025](ADR-0025-gauge-cost-vs-charge-rate.md), [ADR-0027](ADR-0027-touch-limit-rally-gate.md) |
| 반영 | `docs/architecture/04-bot-writing-guide.md` §6.6, 예제 봇 2종(`claw_*_bot.js`) — **엔진/규칙 코드는 바꾸지 않았다** |

## 배경

`develop`에서 자기 진영 연속 터치 제한(`MAX_TOUCHES_PER_SIDE = 5`)이 들어왔다. 한 진영이 공을
네트 너머로 보내지 않고 5번 접촉하면 상대 득점이다. 목적은 명확하다 — 원작에는 상한이 없어서 잘
짠 봇 둘이 붙으면 랠리가 끝나지 않는다.

문제는 **원작 기본 AI의 스매시 판단이 이 규칙을 전제하지 않는다**는 점이다.
`decideWhetherInputPowerHit()`([`physics.js:905-951`](../../../src/resources/js/physics.js#L905-L951))는
`(xDirection, yDirection)` 6개 조합의 착지점을 시뮬레이션해서

- 상대 코트에 떨어지고, **또한**
- 착지점이 상대로부터 `PLAYER_LENGTH`(64px) 넘게 떨어져 있는

조합을 찾는다. **하나도 없으면 `false`를 반환하고 아예 안 친다.** 원작에서는 그게 공짜였다 —
자기 진영에서 공을 무한히 띄우며 좋은 기회를 기다리면 된다. 지금은 그러면 5회 만에 실점한다.

## 측정

기본 AI의 로직을 그대로 이식한 봇으로 90~120초 대전을 돌린 결과:

| | 랠리 종료 원인 (착지 / 터치 제한) | 자기 진영 접촉수 | 점수 |
|---|---|---|---|
| 이식 직후 | 4 / **7** | 52 (상대 11) | 3 : 8 (패) |
| 다른 판 | 0 / **6** | 46 (상대 22) | 2 : 4 (패) |

접촉수 52는 랠리당 약 5회로 상한에 붙어 있다는 뜻이다. 봇이 자기 진영에서 공을 튕기다 그대로
헌납하고 있었다.

조건을 **"상대 코트에 떨어지기만 하면 상대 근처라도 친다"** 로 완화하자(64px 조건은 있으면 쓰고
없으면 포기) 같은 상대 기준으로:

| | 랠리 종료 (착지 / 터치 제한) | 점수 |
|---|---|---|
| 완화 후 (LEFT) | 8 / **자기 진영 0회** (상대 7회) | **14 : 1** |
| 완화 후 (RIGHT) | 13 / **자기 진영 0회** (상대 2회) | **10 : 5** |

터치 제한 실점이 판당 4회에서 **0회**가 됐다. 규칙을 몰랐던 게 아니라, 규칙에 맞지 않는 전략을
원작에서 그대로 베낀 것이 원인이었다.

## 왜 이게 대회 문제인가

[`04-bot-writing-guide.md`](../../architecture/04-bot-writing-guide.md)는 참가자에게 기본 AI를
참고 대상으로 제시하고 있고, `physics.js`는 읽을 수 있는 코드다. **성실한 참가자일수록 기본 AI를
먼저 읽고, 그대로 베끼고, 이유를 모른 채 진다.** 에러도 경고도 안 나므로 디버깅이 어렵다 — 실제로
이 프로젝트에서 그 경로를 한 번 그대로 밟았다.

## 이미 한 것

[`04-bot-writing-guide.md` §6.6](../../architecture/04-bot-writing-guide.md)에 명시했다. 예제 봇
2종을 등재하면서, 엔진을 안 읽으면 알기 어려운 사실 3가지 중 하나로 "**5회 터치 제한이 전략을
바꾼다 — 원작 AI의 '확실할 때만 스매시'를 그대로 베끼면 이 빌드에서는 손해**"를 적었다.

## 아직 OPEN인 것 (회의 안건)

1. **`MAX_TOUCHES_PER_SIDE = 5`가 적정한가.** 5는 "실제 배구는 3회지만 봇이 리시브를 흘렸을 때
   회복할 기회를 주려고 느슨하게" 잡은 값이다(`touchLimit.js` 주석).

   **이 규칙은 의도대로 작동하고 있다.** 위 표에서 터치 제한 실점은 스매시를 못 하는 봇에만
   몰렸고(판당 6~7회), 봇을 고치자 **양 진영 0회**가 됐다. 즉 공을 넘길 줄 아는 봇에게는 아예
   걸리지 않는 안전장치이고, 목적(고장난 봇이 공을 붙들고 경기를 세우는 것 방지)에 정확히
   부합한다. 따라서 **바꿔야 할 적극적인 이유는 현재 없다.**

   다만 대회 당일 참가자 봇의 완성도가 낮으면 이 규칙이 승패를 가르는 비중이 커진다. 그건
   규칙 문제가 아니라 봇 문제이므로, 수치를 손대기보다 §6.6 문서화로 대응하는 쪽이 맞다고 본다.
   회의에서는 "그대로 둔다"를 기본안으로 확인만 하면 충분할 것 같다.
2. **터치 횟수를 스냅샷에 노출할 것인가.** 지금 봇은 자기가 몇 번 만졌는지 알 수 없다. 스스로
   세면 되지만 접촉 플래그가 스냅샷에 없어서 추정만 가능하다. 노출하면 "이번이 4번째니 무조건
   넘긴다" 같은 전략이 가능해진다 — 규칙을 알고도 셀 수 없는 현재 상태보다는 공정하다.
   노출하면 CONTRACTS 필드 추가이므로 **버전을 올려야 한다**(VERIFY §4).
3. **가이드 문서화로 충분한가, 규칙을 바꿔야 하는가.** 문서에 적어두는 것과, 원작 AI를 베껴도
   손해가 아니도록 규칙을 조정하는 것은 다른 선택이다. 대회 성격상 "함정을 문서로 안내"가
   맞는지 "함정 자체를 없애기"가 맞는지는 팀 판단이다.

## 트레이드오프 메모

- 완화한 조건("상대 근처라도 친다")은 **상대에게 받기 좋은 공을 주는 것**이기도 하다. 예제 봇이
  이겼다고 해서 이 전략이 최적이라는 뜻은 아니고, "안 치는 것보다 낫다"는 뜻이다. 참가자가 더
  나은 절충(예: 남은 터치 수에 따라 조건을 단계적으로 완화)을 찾을 여지를 남겨둔 상태다.
- 터치 제한으로 난 득점은 운영자 콘솔의 `awardPoint()`를 그대로 탄다. 즉 자동 규칙과 심판 수동
  득점이 같은 경로를 쓴다(`touchLimit.js` 헤더 주석). 이 설계는 유지하는 게 맞다.
