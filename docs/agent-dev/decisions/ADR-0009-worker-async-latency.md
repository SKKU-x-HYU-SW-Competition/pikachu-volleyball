## 배경 (왜 막혔는지, 구현 중 발견)

[ADR-0003](ADR-0003-bot-execution-sandboxing.md)에서 봇 코드를 Web Worker에서 돌리기로 확정했는데,
Phase 1을 실제로 구현하다 보니 `gameLoop()`은 여전히 완전히 동기 함수이고(§1.0 pseudocode가 가정한
것처럼) 메인 스레드에서 Worker의 응답을 "그 틱 안에" 기다렸다가 반영하는 게 불가능하다는 걸 발견함.
브라우저는 메인(UI) 스레드에서 `Atomics.wait`로 블로킹하는 걸 아예 막아뒀고(워커 스레드에서만
허용), `postMessage`는 본질적으로 비동기라 "요청 보내고 그 자리에서 동기적으로 응답 받기"가 불가능함.

## 결정

**"마지막으로 받은 응답을 그대로 쓰고, 다음 틱 요청은 백그라운드로 흘려보내는" fire-and-forget
방식으로 확정.** 매 틱(또는 `tickFrameGroupSize`마다) `getInput()`은 가장 최근에 Worker로부터 도착한
액션을 동기적으로 적용하고, 이번 틱의 스냅샷은 비동기로 Worker에 보낸 뒤 응답을 기다리지 않고
리턴함. 응답이 도착하면(보통 다음 틱 즈음) `latestAction`을 갱신. 결과적으로 **봇의 반응에 대략
1틱(~40ms) 정도의 파이프라인 지연**이 항상 존재하게 됨 — 이건 버그가 아니라 구조적 특성으로 문서화.
대안(전체 게임 루프를 PixiJS Ticker의 동기 콜백에서 async 루프로 뜯어고쳐 진짜 "그 틱을 기다렸다가
진행"하게 만드는 것)은 렌더링/슬로모션 타이밍 등 기존 동작 전반을 건드리는 위험이 커서 Phase 1
범위에서는 채택하지 않음 — 나중에 이 지연이 실제로 문제가 된다고 판단되면 재검토.
