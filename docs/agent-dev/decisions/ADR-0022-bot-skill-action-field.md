## 배경

[ADR-0021](ADR-0021-claw-skill.md)의 「claw」는 1차 구현에서 **키보드 전용**이었고, 범위는 "발동
시점 상대 위치 중심"으로 자동 결정됐다. 그러나 이 대회의 실제 대전 주체는 사람이 아니라 **봇**이다.
봇이 스킬을 쓸 수 없으면 스킬 시스템 자체가 대회에서 죽은 기능이 되고, 봇이 쓰더라도 조준을 못 하면
"어디를 노릴까"라는 이 스킬의 유일한 전략적 선택이 사라진다.

그래서 팀장이 **봇이 x를 직접 지정**하도록 결정했다. 이건 [CONTRACTS.md](../CONTRACTS.md)가 SOR인
봇 출력 프로토콜 변경이므로 문서를 v0.6으로 올린 뒤 코드를 고쳤다 (VERIFY.md §4 절차).

## 결정

### 1. 필드 형식: `skillX` 하나 (팀장 선택)

```js
function decide(snapshot) {
  return { x: 0, y: 0, hit: 0, skillX: 300 }; // 300을 중심으로 발동
}
```

```python
def decide(snapshot):
    return {'x': 0, 'y': 0, 'hit': 0, 'skillX': 300}
```

- 숫자면 **그 x를 중심**으로 발톱을 예약하고, **생략하거나 `null`이면 미발동**이다.
- 대안이었던 `{skill: 0|1, skillX: n}` 2필드 방식은, 지금은 스킬이 하나뿐이라 "발동 여부"와 "위치"를
  굳이 나눌 이유가 없어서 채택하지 않았다. 스킬이 여러 개가 되면 `skill`을 스킬 ID로 되살리는 확장이
  자연스럽다.

### 2. 좌표 범위: 코트 전체 `0 ~ 432`, 벗어나면 클램프 (팀장 선택)

- 자기 진영을 노리는 것도 막지 않는다 — 손해일 뿐 반칙이 아니고, 규칙이 하나 줄어든다.
- "상대 진영만" 제한은 네트 근처를 노리는 전략까지 같이 막아서 채택하지 않았다.
- 범위 밖 값은 **거절이 아니라 클램프**다. 벽에 1px 붙였다고 발동이 조용히 사라지면 참가자가
  디버깅할 방법이 없다.

### 3. 잘못된 값은 "그 틱의 발동만" 무시

`skillX`가 숫자가 아니거나 `NaN`/`Infinity`면 **발동만 취소**하고 `x`/`y`/`hit`은 그대로 적용한다.
[D-002](ADR-0002-timeout-and-invalid-response.md)의 "잘못된 반환값 → 무입력"을 액션 전체에 적용하면,
스킬 필드 오타 하나로 봇이 그 틱 동안 멈춰 서는 과한 벌칙이 된다. `skillX`는 기존 3필드와 달리
엔진 입력이 아니라 엔진 밖 스킬 계층이 읽는 값이므로 실패 단위도 그만큼만 잡는다.

### 4. 응답 1건당 최대 1회 발동

한 틱은 `TICK_FRAME_GROUP_SIZE`(현재 3) 프레임 동안 유지되고 그동안 같은 액션이 매 프레임
재적용된다([D-009](ADR-0009-worker-async-latency.md)). `skillX`를 매 프레임 읽으면 같은 응답 하나로
게이지를 세 번 내는 셈이 되므로, `PikaBotInput`이 값을 `pendingSkillX`에 담아두고 스킬 계층이
`consumeSkillX()`로 **한 번 읽고 비운다**.

### 5. 하위 호환

`skillX`가 없는 기존 봇은 그대로 동작한다. `isValidBotAction()`은 3필드만 검사하므로 필드가 더 붙어도
액션이 무효가 되지 않는다. 참가자 배포 문서([04-bot-writing-guide.md](../../architecture/04-bot-writing-guide.md))에도
"선택 필드"로 적었다.

### 6. 키보드는 그대로

사람이 키보드로 테스트할 때는 좌표를 입력할 방법이 없으므로 **발동 시점 상대 위치 중심**이라는 기존
동작을 유지한다. 두 경로 모두 같은 `ClawTracker.tryCast()`를 호출하고 조준값만 다르다
(`aimX === null`이면 상대 위치).

## 아직 OPEN인 것

**스냅샷(§1.2) 확장은 이번 버전에 넣지 않았다** (팀장 요청: 스킬 쪽을 먼저 커밋하고 스냅샷은 이어서
작업). 그래서 지금 봇은:

- 자기/상대 **게이지를 볼 수 없다** → 언제 발동 가능한지 모르고, 실패하면 조용히 무시된다.
- 자기를 노린 **예고 중인 발톱을 볼 수 없다** → **회피가 구조적으로 불가능**하다. 사람은 화면을 보고
  피할 수 있으므로 현재 상태는 봇에게 일방적으로 불리하다. 스냅샷 확장 전까지는 밸런스 판단을
  보류해야 한다.

## 트레이드오프

- **액션에 필드를 하나 더 얹은 것** 자체가 "엔진의 3필드를 그대로 미러링한다"는 §1.0 설계 원칙에서
  처음으로 벗어난 지점이다. 스킬은 엔진 밖 계층이라 어차피 1:1 대응이 불가능하고, 필드를 늘리는 대신
  별도 채널(예: 두 번째 반환값)을 두면 참가자 쪽 시그니처가 복잡해진다고 판단했다.
- **`consumeSkillX`가 `keyboardArray` 원소의 선택적 메서드**라는 점이 다소 암묵적이다. 대신 스킬
  계층이 "이 side가 봇인지 키보드인지"를 알 필요가 없어져서, 모드 조합(키보드/봇/기본 AI)이 늘어도
  분기하지 않는다.
