# 팀 온보딩 — 협업 & 개발 환경 (첫 회의용)

> 이 문서는 **코드/게임 로직 내용이 아니라, "우리가 어떻게 같이 개발할 것인가"** 만 다룹니다.
> 봇 프로토콜 등 실제 개발 내용은 [CONTRACTS.md](CONTRACTS.md), [PHASES.md](PHASES.md)를 따로 보세요.

## 1. 왜 이런 걸 만들었나

이 저장소는 여러 명이 **각자 다른 에이전트 도구(Claude Code, Codex CLI 등)를 쓰면서** 동시에 작업할
걸 전제로 합니다. 이런 조건에서 흔히 터지는 문제들:

- 도구마다 다른 진입 파일(`CLAUDE.md` vs 자체 컨벤션)을 봐서 규칙이 갈라짐
- 같은 값(틱 길이, 프로토콜 필드 등)을 파일마다 다르게 정의해서 코드가 어긋남
- "누가 뭘 왜 그렇게 정했는지"가 대화/머릿속에만 있다가 휘발됨
- 여러 명이 같은 로그 파일 끝에 계속 append하다가 merge conflict
- 에이전트가 애매한 부분을 임의로 확정해버려서 나중에 사람이 재작업

아래 구조는 전부 이 문제들을 하나씩 겨냥한 겁니다.

## 2. 문서 구조 한눈에

```
CLAUDE.md ──(리다이렉트만)──▶ AGENTS.md ◀── 모든 도구가 결국 여기로 옴 (진입점 이중화)
                                 │
                                 ├─ 규칙(§1~7): 프로젝트 개요, 게임 구조, 개발 트랙, 협업 규칙,
                                 │              브랜치 전략, 코딩 컨벤션, 문서 지도
                                 │
                                 └─ docs/agent-dev/
                                      ├─ KICKOFF.md    — 세션 시작 시 복붙하는 프롬프트
                                      ├─ CONTRACTS.md  — 봇 프로토콜 SOR (버전 관리됨, DRAFT)
                                      ├─ PHASES.md     — 트랙별 진행 상태 (stub확정→codegen→구현)
                                      ├─ VERIFY.md     — 커밋 전 로컬 체크리스트 (CI 대체)
                                      ├─ TRACKER.md    — 커밋 이력 로그 (회의 준비용)
                                      ├─ DECISIONS.md  — 결정 "인덱스"
                                      └─ decisions/
                                           └─ ADR-NNNN-slug.md  — 결정 하나당 파일 하나
```

핵심 원칙 한 줄씩:

| 장치 | 막는 문제 |
|---|---|
| **진입점 이중화** (CLAUDE.md=리다이렉트, AGENTS.md=진실) | 도구별로 규칙이 갈라지는 것 |
| **CONTRACTS.md 하나만 SOR** | 같은 값이 파일마다 다르게 정의되는 것 |
| **Phase 순차 개발** (stub확정 → codegen → 구현) | 트랙 간 인터페이스가 서로 다르게 짜이는 것 |
| **KICKOFF.md** | 세션마다 컨텍스트를 처음부터 다시 설명하는 비용 |
| **VERIFY.md (로컬 체크리스트, CI 아님)** | "돌아가는지"는 각자 확인, "이 방향이 맞는지"는 회의에서 사람이 판단 |
| **TRACKER.md** | 누가 뭘 했는지 회의 전에 안 보이는 것 |
| **decisions/ADR-NNNN 하나당 파일 하나** | 여러 명이 같은 로그 파일 끝에 동시에 쓰다가 나는 conflict |
| **"모르면 stub + 등재"** | 에이전트가 애매한 걸 멋대로 확정해버리는 것 |

## 3. 지금까지 진행 상황

- **Phase 1 (입력 구조 개편)** — 완료. 참가자 봇 코드를 Web Worker에서 격리 실행하고, 매 틱
  게임 상태 스냅샷을 주고 `{x, y, hit}`를 받아 기존 `keyboardArray`에 꽂는 구조 (`src/resources/js/bot/`).
- **Phase 2 (테스트 환경)** — 완료. 좌/우 진영을 각각 [키보드 | 내 봇 코드 | 기본 AI]로 자유롭게
  조합해서 붙어볼 수 있는 "Bot Setup" 패널 (게임 메뉴바에서 접근).
- **결정 로그**: ADR 10개 확정 (틱 길이, 타임아웃 처리, 샌드박싱 방식, 좌표계, 세트제 미도입 등).
  자세한 내용은 [DECISIONS.md](DECISIONS.md) 인덱스에서 목록만 보고, 필요하면 개별 ADR 파일 열어보면 됨.
- Phase 3(제출/중계), Phase 4(스킬/에셋)는 아직 착수 전.

## 4. 오늘부터 팀 운영 방식

### 브랜치 전략

- **`main`**: 항상 배포 가능한 상태만. 직접 커밋 금지.
- **`develop`**: 통합 브랜치. 모든 작업은 여기서 분기하고 여기로 merge.
- **`feature/<이슈번호>-<짧은설명>`**: 실제 작업 단위. 예: `feature/12-bot-submission-form`.

```
main ──────────────────────────────────(릴리즈 시점에만 merge)
  ▲
develop ──●──────●──────●──────────────
          │      │      │
          ▼      ▼      ▼
   feature/12  feature/13  feature/14   (각자 이슈 하나씩 붙잡고 작업)
```

### GitHub Issue 활용

1. 작업 시작 전 이슈를 만든다 (없으면).
2. 이슈 번호를 브랜치 이름에 넣는다: `feature/12-...`.
3. PR 설명에 `Closes #12`를 적는다 — merge되면 이슈가 자동으로 닫힘.
4. 관련 ADR이 있으면 PR 설명에 ADR 번호도 같이 적는다 (리뷰어가 "왜 이렇게 짰는지" 바로 찾아가게).

### 결정(ADR) 남기는 법이 바뀜

기존에는 `DECISIONS.md` 한 파일에 계속 append했는데, 사람이 늘어나면 이 파일 끝부분에서 충돌이
잦아질 게 뻔해서 **결정 하나당 파일 하나**(`docs/agent-dev/decisions/ADR-NNNN-slug.md`)로
바꿨습니다. `DECISIONS.md`는 이제 목록만 보여주는 인덱스입니다. 절차는 그대로: 애매하면 멋대로
정하지 말고 stub + 새 ADR 파일 등록 → 회의에서 결정 → RESOLVED로 갱신.

### 리뷰 방식은 그대로

CI/CD 없음. 커밋 전 `VERIFY.md` 체크리스트를 각자 로컬에서 돌리고, 실제 "이 방향이 맞나"는 정기
회의에서 `TRACKER.md` 로그를 보며 사람이 리뷰합니다.

## 5. 새 세션/새 작업을 시작할 때 (매번 반복)

1. `AGENTS.md`부터 읽는다 (또는 `docs/agent-dev/KICKOFF.md`의 프롬프트를 그대로 복붙해서 에이전트에게 준다).
2. `develop`에서 `feature/<이슈번호>-설명` 브랜치를 딴다.
3. 작업 중 애매한 게 나오면 멋대로 정하지 말고 stub + 새 ADR 등록.
4. 커밋 전 `VERIFY.md` 체크리스트 실행.
5. `TRACKER.md`에 기록 추가.
6. PR을 `develop`로 연다 (이슈/ADR 번호 언급).
7. 정기 회의에서 `TRACKER.md`를 보며 리뷰.
